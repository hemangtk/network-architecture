# Annotated hexdump: one complete request and response

*Author: Hemang (Roll No. 24bcs10209)*

This is a real capture, not a hand-drawn one. It was produced with:

```
$ ./bserve ./www 9000 &
$ ./bcurl -vv localhost:9000/hi.txt 2> hexdump-capture.txt
hi
```

`-v` prints every frame as a classic hexdump. `-vv` also prints the
annotation table under each frame. The annotation is generated by walking the
frame with the rules in `SPEC.md`. The unedited output is in
[`hexdump-capture.txt`](hexdump-capture.txt). Arrows show direction:
`>` is client to server, `<` is server to client.

Totals:

| Direction | Frames | Octets |
|---|---|---|
| Client to server | preface + 1 HEADERS | 4 + 65 = 69 |
| Server to client | 1 HEADERS + 1 DATA | 102 + 11 = 113 |
| Client goodbye | 1 GOAWAY | 12 |

## 1. Request: preface + HEADERS (client to server)

```
> PREFACE
>   00000000  42 48 50 01                                       |BHP.|
> HEADERS stream=1 len=57 flags=END_STREAM
>   00000000  00 00 39 01 01 00 00 01  01 00 03 47 45 54 02 00  |..9........GET..|
>   00000010  07 2f 68 69 2e 74 78 74  04 00 09 6c 6f 63 61 6c  |./hi.txt...local|
>   00000020  68 6f 73 74 05 00 14 62  63 75 72 6c 2f 31 20 28  |host...bcurl/1 (|
>   00000030  32 34 62 63 73 31 30 32  30 39 29 06 00 03 2a 2f  |24bcs10209)...*/|
>   00000040  2a                                                |*|
>   0000  00 00 39                                         Length = 57 (payload octets after this 8-octet header)
>   0003  01                                               Type = 0x01 HEADERS
>   0004  01                                               Flags = 0x01 END_STREAM
>   0005  00 00 01                                         Stream ID = 1
>   0008  01                                               field: idx 0x01 = :method
>   0009  00 03                                            value length 3
>   000b  47 45 54                                         value "GET"
>   000e  02                                               field: idx 0x02 = :path
>   000f  00 07                                            value length 7
>   0011  2f 68 69 2e 74 78 74                             value "/hi.txt"
>   0018  04                                               field: idx 0x04 = host
>   0019  00 09                                            value length 9
>   001b  6c 6f 63 61 6c 68 6f 73 74                       value "localhost"
>   0024  05                                               field: idx 0x05 = user-agent
>   0025  00 14                                            value length 20
>   0027  62 63 75 72 6c 2f 31 20 28 32 34 62 63 73 31 30  value "bcurl/1 (24bcs10209)"
>   0037  32 30 39 29                                        (cont.)
>   003b  06                                               field: idx 0x06 = accept
>   003c  00 03                                            value length 3
>   003e  2a 2f 2a                                         value "*/*"
```

How to read it:

- `42 48 50 01` is the preface: `"BHP"` then version 1. It is sent once per
  connection, not once per request.
- `00 00 39` means the payload is 0x39 = 57 octets. The receiver now knows
  this frame ends at offset 8 + 57 = 65, and that octet 66 is the start of the
  next frame. That answers the question from the assignment ("where does this
  request end?") before any payload octet has been read.
- `01` is HEADERS, and `01` is END_STREAM: this GET has no body. `00 00 01`
  is stream 1.
- Every field is `index`, then a 2-octet length, then the value. Five of the
  ten static-table names appear here (`:method`, `:path`, `host`,
  `user-agent`, `accept`), so no header name is spelled out on the wire.
- The same request in HTTP/1.1 text (`GET /hi.txt HTTP/1.1` plus Host,
  User-Agent and Accept) is 88 octets. In BHP/1 it is 65, and it can be parsed
  without searching for `\r\n`.

```
< HEADERS stream=1 len=94 flags=-
<   00000000  00 00 5e 01 00 00 00 01  03 00 03 32 30 30 07 00  |..^........200..|
<   00000010  19 74 65 78 74 2f 70 6c  61 69 6e 3b 20 63 68 61  |.text/plain; cha|
<   00000020  72 73 65 74 3d 75 74 66  2d 38 08 00 01 33 09 00  |rset=utf-8...3..|
<   00000030  15 62 73 65 72 76 65 2f  31 20 28 32 34 62 63 73  |.bserve/1 (24bcs|
<   00000040  31 30 32 30 39 29 0a 00  1d 46 72 69 2c 20 32 35  |10209)...Fri, 25|
<   00000050  20 53 65 70 20 32 30 32  36 20 31 33 3a 33 36 3a  | Sep 2026 13:36:|
<   00000060  33 34 20 47 4d 54                                 |34 GMT|
<   0000  00 00 5e                                         Length = 94 (payload octets after this 8-octet header)
<   0003  01                                               Type = 0x01 HEADERS
<   0004  00                                               Flags = 0x00
<   0005  00 00 01                                         Stream ID = 1
<   0008  03                                               field: idx 0x03 = :status
<   0009  00 03                                            value length 3
<   000b  32 30 30                                         value "200"
<   000e  07                                               field: idx 0x07 = content-type
<   000f  00 19                                            value length 25
<   0011  74 65 78 74 2f 70 6c 61 69 6e 3b 20 63 68 61 72  value "text/plain; charset=utf-8"
<   0021  73 65 74 3d 75 74 66 2d 38                         (cont.)
<   002a  08                                               field: idx 0x08 = content-length
<   002b  00 01                                            value length 1
<   002d  33                                               value "3"
<   002e  09                                               field: idx 0x09 = server
<   002f  00 15                                            value length 21
<   0031  62 73 65 72 76 65 2f 31 20 28 32 34 62 63 73 31  value "bserve/1 (24bcs10209)"
<   0041  30 32 30 39 29                                     (cont.)
<   0046  0a                                               field: idx 0x0a = last-modified
<   0047  00 1d                                            value length 29
<   0049  46 72 69 2c 20 32 35 20 53 65 70 20 32 30 32 36  value "Fri, 25 Sep 2026 13:36:34 GMT"
<   0059  20 31 33 3a 33 36 3a 33 34 20 47 4d 54             (cont.)
```

- The flags are `00`, not END_STREAM, so a body follows in DATA frames on the
  same stream.
- `:status` is sent as the three ASCII digits `"200"` (index `03`). This
  keeps every value in one uniform encoding, a length-prefixed string.
- `content-length "3"` tells the client how many body octets to expect across
  all DATA frames. `bcurl` checks it and treats a mismatch as a protocol error
  (exit code 3).

## 3. Response DATA (server to client)

```
< DATA stream=1 len=3 flags=END_STREAM
<   00000000  00 00 03 00 01 00 00 01  68 69 0a                 |........hi.|
<   0000  00 00 03                                         Length = 3 (payload octets after this 8-octet header)
<   0003  00                                               Type = 0x00 DATA
<   0004  01                                               Flags = 0x01 END_STREAM
<   0005  00 00 01                                         Stream ID = 1
<   0008  68 69 0a                                         body "hi\n"
```

- Type `00` is DATA and flag `01` is END_STREAM: this is the last frame of
  the response. Stream 1 matches the request.
- The payload `68 69 0a` is `"hi\n"`, 3 octets, which matches
  `content-length`. Longer files are split into DATA frames of 16 384 octets
  (the tests check a 100 000-octet file arrives as 7 frames).
- The connection is still open. `bcurl` could send stream 2 now over the same
  socket.

## 4. Goodbye (client to server)

```
> GOAWAY stream=0 len=4 flags=-
>   00000000  00 00 04 02 00 00 00 00  64 6f 6e 65              |........done|
>   0000  00 00 04                                         Length = 4 (payload octets after this 8-octet header)
>   0003  02                                               Type = 0x02 GOAWAY
>   0004  00                                               Flags = 0x00
>   0005  00 00 00                                         Stream ID = 0
>   0008  64 6f 6e 65                                      reason "done"
```

GOAWAY on stream 0 with an optional UTF-8 reason. The server logs
`client GOAWAY after 1 requests` and closes.

## 5. An unknown frame being skipped

This is from `./bserve --grease`, which sends frame type `0xFA` before every
response to prove that clients follow the rule to skip unknown types:

```
* unknown frame type 0xfa (21 octets) skipped
< UNKNOWN(0xfa) stream=1 len=21 flags=-
<   00000000  00 00 15 fa 00 00 00 01                           |........|
```

The client reads the 8-octet header, sees type `0xFA`, discards exactly
0x15 = 21 payload octets without interpreting them, and carries on with the
next frame. That is the whole v2 compatibility mechanism.
